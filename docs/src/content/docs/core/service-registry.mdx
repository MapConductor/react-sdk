# MapServiceRegistry

`MapServiceRegistry` is a small typed registry used internally to attach optional, map-scoped services — the kind of thing an extension package (like marker clustering's native strategy, or a future plugin) needs to reach without every provider controller knowing about it by name.

## Interface

```ts
interface MapServiceKey<T> {
  readonly __brand: T; // phantom type only — carries no runtime value
}

function createMapServiceKey<T>(): MapServiceKey<T>;

interface MapServiceRegistry {
  get<T>(key: MapServiceKey<T>): T | null;
}
```

A key created with `createMapServiceKey<T>()` is what makes lookups type-safe — `registry.get(key)` returns `T | null` without a cast, and two keys are never accidentally interchangeable even if `T` happens to match.

## Registering and retrieving a service

```ts
const registry = new MutableMapServiceRegistry();

const analyticsKey = createMapServiceKey<AnalyticsService>();
registry.put(analyticsKey, new AnalyticsService());

const analytics = registry.get(analyticsKey); // AnalyticsService | null
```

`EmptyMapServiceRegistry` is a no-op implementation (`get()` always returns `null`) — the value `useMapServiceRegistry()` reports outside of any map.

## Scope

Every map view owns one registry, reachable as `state.serviceRegistry`, and provides it to its
children through `MapServiceRegistryProvider`. Extensions read it with `useMapServiceRegistry()`.
This is the React counterpart of Android's `LocalMapServiceRegistry` CompositionLocal and iOS's
`MapServiceRegistryScope.current`.

The registry is provided through its own React context, separate from the marker/overlay
collectors. That matters for components like `MarkerClusterGroup`, which create their own
`MapViewScope` for their children: the collector is shadowed inside the group, the registry is not.

## What's registered today

Every `react-for-*` provider registers `MarkerRenderingSupport` under `MarkerRenderingSupportKey`:

```ts
import {
  createCollectorMarkerRenderingSupport,
  MarkerRenderingSupportKey,
} from '@mapconductor/js-sdk-core';

state.serviceRegistry.put(
  MarkerRenderingSupportKey,
  createCollectorMarkerRenderingSupport({ collector, holder }),
);
```

In practice a provider just calls the `useMarkerRenderingSupport(state, scope, controller)` hook,
which registers the default implementation and takes it back on unmount.

`react-marker-clustering` resolves that capability instead of building a marker renderer itself:

```ts
const services = useMapServiceRegistry();
const renderingSupport = services.get(MarkerRenderingSupportKey);
const renderer = renderingSupport?.createMarkerRenderer(strategy);
```

This is the same two-step (`createMarkerRenderer` → `createMarkerEventController` →
`registerMarkerEventController`) that `MarkerClusterGroup.kt` and `MarkerClusterGroup.swift` use,
so a provider never has to implement a plugin's interfaces and a plugin never has to know which
provider it is running on.

## When you'd use this

Most application code never touches `MapServiceRegistry` directly — it's infrastructure for
extension packages and provider internals to share optional services within a map's scope without
introducing a hard dependency between packages. If you're building your own extension package in
the same style as `react-heatmap` or `react-marker-clustering`, this is the mechanism for exposing
a service to other code sharing the same map view without threading it through every component's
props.
